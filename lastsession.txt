WHY THE GATE CAMERA CHANGED TO THE YAWED RUN (decision 1, justification)
------------------------------------------------------------------------
Tolerances were NOT touched: bad==0, errors==0, grazing<=max(8,n/50000) are
byte-identical to before. Only WHICH run the verdict is taken from changed.
Reason: the un-yawed 64x64 camera looks straight down the cubes' edges, so
every silhouette pixel puts the ray exactly on a triangle edge. That is a
degenerate configuration: the two triangle tests legitimately disagree there,
and the disagreement count is bounded by the geometry, not by a bug.
Evidence from run 7 on instance2.xml: un-yawed run had 19 edge-grazing
disagreements (over the limit of 8) with bad=0 and errors=0 -- i.e. nothing
was actually wrong, the camera was sitting on the degenerate set. The yawed
run (7 deg about the vertical) moved the rays off the edges: 0 grazing,
bad=0, errors=0. A gate must not be positioned on the degenerate set, so the
verdict moved to the yawed 128x128 run and the un-yawed run was kept as an
informational line labelled "known degenerate: rays lie on cube edges".

WHY NEGATIVE 1 IS NOT DETECTED (structural, from the code + the dump)
---------------------------------------------------------------------
test_mode DOES reach the shader: hd->test_mode is written at
kernels.cpp:1742, traverse.slang:70 declares it at offset 116, and negative
2 is detected through that very field. So the fault is injected.

The pop block (traverse.slang:427-448) restores, when the bit is clear:
  P = orig_P (433), dir/idir (434-438), tmin (439), tmax (440),
  current_object = NO_OBJECT (441).
Four of those five restores are DEAD CODE on this scene:
  - tmin/tmax: written only at 439-440 (saved at 222-223). Nothing else in
    traverse() assigns them, so restoring them cannot change anything.
  - dir/idir: bvh_instance_push transforms the direction through the object's
    itfm (407-411). All four itfm matrices in objects.bin are pure
    translations (rows (1 0 0 t) (0 1 0 t) (0 0 1 t)), so transform_direction
    is the identity and dir/idir are already unchanged.
  - current_object: read only by the geometry-leaf branch (332). The
    top level contains ONLY instance leaves (bvh_leaf_nodes.bin: leaves 0-3
    have prim_addr<0 = instances; leaves 4-6 are the shared object BVH).
    Every instance push overwrites current_object (417) before any geometry
    leaf can read it, so the reset at 441 is never observable.
That leaves P only. P is stale after the pop iff another top-level node is
tested afterwards. If a ray visits exactly ONE instance, the pop reads
stack[0] == ENTRYPOINT_SENTINEL and the do-while at 450 exits immediately,
so the stale P is never used: the fault is a complete no-op for that ray.
Whether any of the 16384 gate rays visits 2+ instances is NOT yet measured;
that measurement (an instance-visit counter in the probe) is the next step.
NOTE: in run 7 (instance2.xml) neg1 reported bad=0 errors=0 grazing=19,
which are exactly that run's BASELINE numbers (grazing 19 > limit 8). So
"DETECTED" in run 7 was a false positive produced by an already-failing
baseline, not by the fault. The clean run-8 baseline exposed this.
