CONCLUSIONS
 ---------------------------------------------------------------------------
 1. NO slangc layout option fixes the bug. scalar/gl = identical codegen+result;
    c = 28B smaller but same bug; dx = FAILS spirv-val. Do NOT adopt any option
    (none change KernelParamsVulkan/IntegratorStateGPU need; base-ptr works
    everywhere). Root cause is index LOWERING, not layout.
 2. Form B (ONE struct level) is JUST as buggy: Slang inserts the
    _Array_natural wrapper regardless of nesting depth
    (Blob_natural{ _Array_natural_uint8{ uint[8] } }). => ANY fixed-array
    STRUCT MEMBER hit by an inline dynamic index is buggy, at any depth.
 3. Form C (pointer member uint* words) is SAFE by codegen:
    Blob_natural = OpTypeStruct{_ptr_..._uint} (NO OpTypeArray);
    inline index -> OpPtrAccessChain on a FLAT uint*. Matches the proven-safe
    base-ptr/raw/traverse-pointer-member pattern.
 4. SECOND DEVICE (Stage 0c): SwiftShader (Subzero) IS available, forced via
    VK_ICD_FILENAMES=C:\Windows\System32\Microsoft-Edge-WebView\vk_swiftshader_icd.json
    (self-contained; api 1.0.5; it supports BDA). On SwiftShader the SAME SPIR-V
    runs CORRECTLY: out(a)=10 11 12 13 14 15 16 17. => The SPIR-V is
    SEMANTICALLY VALID; the fault is the AMD RX 570 DRIVER (31.0.21925.1001)
    mishandling OpAccessChain-dynamic-on-nested-array-in-PhysicalStorageBuffer.
    Slang's contribution is emitting the _natural wrapper that creates the
    pattern the AMD driver mishandles. The base-ptr/raw (OpPtrAccessChain on
    flat uint*) workaround sidesteps the AMD driver fault.

FORWARD HAZARD (unchanged, now CONFIRMED to apply at any nesting depth)

BLOCKER FOUND for item 1 (do NOT write accessors until resolved)
 ---------------------------------------------------------------------------
 The `ray`/`isect`/`subsurface` state sub-structs are PACKED
 (state_template.h:78-108, KERNEL_STRUCT_BEGIN_PACKED). So `ray.P`/`ray.D` are
 `packed_float3` = 12-BYTE elements in the SoA data buffer, NOT 16-byte Slang
 float3. A `ray.P[state]` accessor written as `float3*` would use stride 16 and
 silently corrupt the ray (reads garbage from offset state*16 instead of
 state*12). Before writing ANY packed_float3 accessor, the next session MUST
 verify the exact element stride Cycles uses for these SoA buffers (read how
 KERNEL_STRUCT_MEMBER_PACKED + the GPU state allocator size the arrays; confirm
 12 vs 16) and pick a representation (raw 3x float read, packed_float3 helper,
 or uint4/float4 only where genuinely 16B-aligned). This is a "layout comes
 from the real C++" item (AGENTS.md) — do not guess.
 The NON-packed fields (path.*: render_pixel_index/sample/rng_pixel/
 queued_kernel/throughput(PackedSpectrum); volume_stack int object[32]) do NOT
