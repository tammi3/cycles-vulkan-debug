compute backend for Blender's physically-based path tracer, Cycles (Cycles X).

3. CRITICAL HARDWARE QUIRKS & DRIVER WORKAROUNDS (MUST RESPECT)
--------------------------------------------------------------------------------
Past milestone investigations (M4e, M4f) identified severe driver defects in the
RX 570 driver (31.0.21925.1001) and specific limits in SwiftShader:

1. Dynamic Indexing on BDA Fixed Arrays:
   - Driver Bug: AMD driver miscompiles `OpAccessChain` when dynamically indexing
     a fixed-size array inside a `PhysicalStorageBuffer` (BDA) struct (e.g.,
     `params->data.words[i]`), invariably returning element 0.
   - Rule: NEVER dynamically index fixed-size arrays inside BDA structs. Always take
     a base pointer once (`uint* base = &params->data.words[0];`) and index through
     it, or pass a raw pointer view.

2. Pointer OpBitcast Rules:
   - RX 570 Bug: OpBitcasting a `PhysicalStorageBuffer` pointer involving 16-bit
     or 8-bit pointees crashes `vkCreateComputePipelines` with access violation (0xC0000005).
   - RX 570 Atomic Bug: OpBitcasting a pointer before an atomic operation drops the
     element offset, causing the atomic to execute at the buffer's BASE address.
     Workaround: pass the buffer device address twice with distinct types (e.g.,
     `float*` and `uint*` in push constants).
   - SwiftShader Bug: SwiftShader Subzero JIT crashes (0xC00000FD) on ANY pointer-to-pointer
     `OpBitcast` on `PhysicalStorageBuffer` pointers.
   - Rule: Zero pointer OpBitcasts across Slang modules. Perform pointer math in
     typed terms or via integers/scalars.

3. Truncated Pointer Loads (AMDVLK):
   - Driver Bug: `OpLoad` of a struct pointer member is truncated to the innermost
     pointee width (loads 2 bytes for `uint16_t*`, 1 byte for `uint8_t*`).
   - Workaround (Form A): Compute the slot address via integer math (`(uint64_t)ist + offset`),
     cast to `uint64_t*`, load as an 8-byte scalar, and convert with `OpConvertUToPtr`.

4. SwiftShader Capability Constraints:
   - SwiftShader does not support `shaderInt64`, `shaderInt16`, or `shaderInt8`.
   - Shaders intended for dual-device validation must avoid emitting these capabilities
     (e.g., using 32-bit atomic fallback for sub-words in default mode).

4. STRICT OPERATIONAL RULES & METHODOLOGY (AGENTS.md)
--------------------------------------------------------------------------------
1. File Boundaries:
   - Only edit files explicitly permitted by the active task prompt.
   - Never edit `C:\dev\cycles-vulkan`, `agentreference/`, or files outside `src/`
     unless specifically instructed.
   - The verification harness, tolerances, and test images are immutable and sacred.
     If a test fails, the code is wrong, not the test.

2. Translation Fidelity (Cycles C++ -> Slang):
   - Translate faithfully, line-for-line. Do not "improve", refactor, or prematurely
     optimize Cycles logic during translation. Cycles CPU is the ground-truth reference.
   - Cite source file and line on non-trivial logic: `// source: <path>:<line>`.
   - Divergence Exception: Allowed only if strictly necessary for driver workarounds
     or measured faster on the RX 570.
     * Port faithfully first.
     * Gate must pass in faithful mode before any divergence is introduced.
     * Divergence must be guarded behind a macro/specialization constant.
     * Fully documented in `DIVERGENCES.md` with measured timings.
     * No optimization passes before M5 gate is cleared.

3. Slang Language Rules:
   - No virtual dispatch (no interfaces or function pointers in hot execution paths).
     Use explicit `switch` statements over closure / kernel types.
   - Straight-line execution: no recursion.
   - No dynamic allocations or variable-length arrays.
   - 64-bit BDA raw pointers allowed, but never create pointers to function locals
     (use `inout` / `out`).
   - Explicit storage classes: `ccl_private` -> local/inout, `ccl_global` -> BDA pointer,
     `ccl_constant` -> push constants.
   - Layouts must be verified against real C++ headers with `static_assert(offsetof(...))`.
   - Bounds-check all pointer array accesses and cap all loops defensively.

4. Verification Gates & Quality Assurance:
   - Every shader must compile cleanly with `slangc -target spirv` and pass `spirv-val`.
   - Check every `VkResult` in C++ Vulkan host code.
   - All gate runs must have Vulkan validation layers active (`VK_LAYER_KHRONOS_validation`)
     and produce 0 VUID errors and 0 validation errors.
   - Verification policy: raw-bit exact match for integers/pointers; relative float
     tolerance `|gpu - ref| <= 1e-5 * max(1, |ref|)`.
   - Negative tests require a clean baseline; faults must be detected within exact masks
     with zero spillover to unrelated data regions.

5. Communication & Working Style:
   - The user has deep expertise in shader theory and path tracing, but is learning
     C++ and its build systems.
   - Code must be heavily commented: explain WHAT every block does and WHY.
   - Explain design decisions in plain, accessible language.
   - State assumptions upfront in 3-5 bullet points before writing code.
   - Update `lastsession.txt` incrementally after each completed step.
   - Three-strikes rule: if a fix or command fails three times, stop and report.
   - No elevated actions (UAC/admin). No untracked generated files in the repo root.
